# HiTPH Protenix cycle-4 实验现状、加速结果与训练资源预算

**状态快照：2026-10-16 17:38（北京时间）。** 本文区分已完成的实测、正在执行的离线缓存任务，以及尚未实现的在线训练方案。容量均按十进制 TB（10¹² 字节）计；时间估算不等于正式训练工期。

## 1. 固定实验协议与数据

数据来自 `/NAS/luyq/TMP_prediction/data/hitph_l4_v1/splits`。输入是一条完整的 TCRα–TCRβ–peptide–HLA 四链复合物，**无任何链的 MSA**，不运行结构 diffusion/confidence。冻结 Protenix-v1，`cycles=4`、seed 101、BF16 推理；下游使用 `s`、`z`、`p_dist` 和链/残基索引，特征按 FP16 保存或在 GPU 上转 FP16 后直接训练。分类头为 **4-block Pairformer + C 全 attention pooling**。

| 数据部分 | 正例 | 负例 | 总数 | 负例策略 |
|---|---:|---:|---:|---|
| Train，每 epoch | 79,465 | 158,930 | 238,395 | 每轮重新抽取，1:2 |
| Validation | 3,951 | 7,902 | 11,853 | 一次抽取后固定，1:2 |
| 内部 Test | 1,784 | 3,568 | 5,352 | 一次抽取后固定，1:2 |

训练负例由 `scripts/negative_sampling/peptide_mismatch.py` 产生：保持天然配对的 TCRα/β 与 HLA context，将 peptide 换成同一 HLA context 中的合法候选，排除已知 TCR–peptide 阳性组合，并对四链输入去重。使用 seed 42 和 epoch 编号保证每轮可重现；全局负例配额严格为正例的两倍，少数候选不足的组通过其他有容量的组补足。生成后的**每条负例仍需对完整四链运行 Protenix**，不能拼接正例已有的 `s/z/p_dist`。每轮样本计划重新打乱；epoch 1 与预生成的 epoch 2 清单仅有 5,942 条相同负例。

## 2. 缓存任务当前状态与空间

Foldtmp 仅作为挂载存储，主机 Tang1、Tang2、Tang3 的 GPU 负责计算。缓存路径为 `/NAS/luyq/TMP_prediction/protenix_embeddings/hitph_v1/embeddings_cycle4_nomsa_seed101_bf16_fp16_szp_protenixv1/features`；名称保留 cycle 4、无 MSA、seed、推理/缓存精度等关键参数。固定训练正例与固定验证/测试样本已全部缓存：**96,670 条，实际文件总计 6,507,764,746,554 字节（6.508 TB）**。

截至快照，epoch 1 训练负例已完成 **127,995 / 158,930 条（80.5%）**，文件总计 **8,630,397,598,938 字节（8.630 TB）**，剩余 30,935 条；当前固定部分加负例合计约 **15.138 TB**。最近一小时约新增 2,024 条，但这是加速进程逐步启动期间的混合速率，不能直接作为稳定 ETA。按最近一小时速率机械外推，剩余约 15.3 小时；实际会受共享 GPU、SSHFS、分片尾部和故障重试影响。

完整 epoch 1 负例估计约 **10.714 TB**，固定缓存加一轮负例约 **17.222 TB**，低于目前允许的 20 TB 上限，理论余量约 2.78 TB（未包含额外临时文件和文件系统开销）。训练正例单独约 **5.353 TB**；固定验证约 **0.795 TB**，固定测试约 **0.359 TB**。合法训练负例候选池约 5,825 万条，按当前张量形状全部缓存需约 **3.93 PB**，不可作为动态采样的预缓存策略。

已实现的离线轮换流程是在完整 epoch checkpoint 验证后删除该轮训练负例，再准备下一轮；固定样本永久保留，下一轮重复的负例可保留。只有 epoch 1 缓存任务正在执行，**正式训练尚未启动**。epoch 2 输入清单已生成，但在线生成负例的训练 provider、GPU 队列和分布式数据管线尚未实现。

## 3. Protenix 加速版：实测与正在运行的版本

Tang2 的独占 A40 基准使用真实 epoch 1 负例（约 411–430 tokens）、Protenix-v1 cycle 4、无 MSA、4-block 分类头及激活重计算。负例特征保持 GPU→GPU，不复制到 CPU、也不写 `.pt`；每卡 24 条，排除首条热身。cuEquivariance 0.5.1 通过隔离的 CUDA 11 overlay 启用；CUDA 12 版与当前 PyTorch 2.7.1+cu118 环境不兼容。

| 指标，热样本中位 | 原 `torch/torch` | `cuequivariance/cuequivariance` |
|---|---:|---:|
| Protenix 推理/负例 | 11.836 秒 | **约 4.45 秒** |
| 分类头训练/样本 | 1.101 秒 | **约 1.10 秒** |
| 单条完整处理 | 13.443 秒 | **约 6.06 秒** |
| PyTorch 峰值保留 | 约 10.1 GiB | **约 14–15 GiB** |

同卡开两个加速进程未改善总吞吐（24 条约 174.3 秒，对照单进程约 168.9 秒），因此采购与调度按**每 GPU 一个有效训练/推理流水线**估算。4.45 秒是独占 A40 的**无写盘推理**中位数，不是当前共享卡、Foldtmp 写盘提取任务的单条墙钟。切换后正式提取日志中已有约 6–9 秒/条（含保存）的样本，但尚无稳定整轮吞吐数据。

2026-10-16 已在 Tang1、Tang2、Tang3 分别做一条真实负例的加速本地短测；随后将 epoch 1 未完成的 11 个分片按原编号续跑，所有当前活动提取进程均携带 `--trimul-kernel cuequivariance --triatt-kernel cuequivariance`。自动协调器 `hitph_epoch1_coord_accel_20261016` 监控重启和最终索引合并。旧缓存文件不重算；新文件内有 `kernel_backend=cuequivariance/cuequivariance`，无此字段的旧文件按 `torch/torch` 识别。用户已明确允许这一轮混用。

**数值风险仍在。** 一条同样本旧缓存与加速短测特征的 `z` 平均绝对差为 1.114、`p_dist` 为 0.00058；此前原算子重复运行也存在较大波动，现有小样本不能证明两路径等价。所有正例来自旧路径，而部分训练负例来自新路径，分类头可能学习算子来源而非结合特征。正式评价至少应按来源分层，最好在受控随机状态下扩样比较并检查来源可预测性；不能把此轮混合缓存当作已验证的等价数据。

## 4. 训练方式与单机八卡时间

计划的在线方案：每个 DDP rank 常驻冻结 Protenix 和可训练分类头；正例从固定缓存异步读取；每轮按 seed 42 + epoch 生成负例计划，在 GPU 上推理当前完整负例，转 FP16 后直接交给同卡分类头做前向/反向，**不写或重读训练负例特征**。模型仅更新分类头。首版以每卡 microbatch 1、激活重计算、CPU/I/O 预取和 GPU 串行调度为基线；GPU 双 stream 或独立生产者 GPU 仅在端到端实测改善后采用。全局有效 batch 24（8 卡 × 梯度累积 3）是建议起点，不是已完成训练的配置。固定验证集每轮评估，最终再评估固定测试集。

在 Tang2 独占 A40 的热样本中位数上，纯 GPU 工作量为：

`158930 × 4.45 s（负例 Protenix）+ 238395 × 1.10 s（全部样本分类头）= 269.30 A40-GPU·小时`。

若八张 A40 **独占、等速、完美均衡**，单轮计算下界为 **33.66 小时，约 1.40 天**。若每条负例约 0.43 秒 CPU 特征准备完全不能与 GPU 工作重叠，则八卡增加约 2.37 小时，约 **36.04 小时**。以上均未计 Foldtmp 正例冷读、DDP 同步、验证、checkpoint、启动编译和长度长尾；尚未跑通八卡在线训练，因此没有可信的实测端到端 epoch 时间。

“负例不读写盘”不代表训练完全无磁盘 I/O：每轮仍要读取约 **5.353 TB** 已缓存正例，固定验证也要读取。若要求训练期间连正例特征也不读盘，需提前放入至少约 5.35 TB 可用主机内存（预加载时间另计），或者正例也在线推理；后一方案计算量升至约 **367.53 A40-GPU·小时**，八卡理论下界 **45.94 小时**，且不含验证。

作为对照，先前 60 条样本的离线头训练试测在 Tang2 A40 上，Foldtmp 冷读约 9.37 秒/条、系统缓存暖读约 2.08 秒/条；两者都不能直接外推在线训练。原始头曾在共享 GPU 上显存紧张；激活重计算的在线组合短测峰值约 14–15 GiB PyTorch 保留，采购仍需预留 CUDA context、最长样本和通信显存。

## 5. 扩容预算与采购判断

下面是**总算量下界**，将 269.30 A40-GPU·小时除以目标时间。`η=0.75` 只是示例并行效率，不是已测效率；目标时间未计验证。正例最低读取速率只按 5.353 TB/epoch 计算。

| 目标/epoch | 理想 A40 等效卡数 | 若 η=0.75 的 A40 卡数 | 正例最低持续读取 |
|---:|---:|---:|---:|
| 24 小时 | 12 | 15 | 62 MB/s |
| 12 小时 | 23 | 30 | 124 MB/s |
| 6 小时 | 45 | 60 | 248 MB/s |
| 3 小时 | 90 | 120 | 496 MB/s |
| 1 小时 | 270 | 360 | 1.49 GB/s |

卡数表**不能直接作为采购数量**。保持有效 batch 24、每步在同卡现算负例并串行训练时，约 9,934 次参数更新，每步至少要等待一条负例的 4.45+1.10 秒；即使加到 24 张 A40，关键路径仍约 **15.3 小时**。若用独立 GPU 预生成后续负例并经 GPU 间传输，batch 24 的分类头更新关键路径约 **3.04 小时**；一小时目标必须增大有效 batch 至约 73 或改变优化语义，纯工作量至少需约 197 张 A40 等效卡供负例生产、约 73 张供头训练，再加通信/验证余量。更大 batch 可能改变收敛，须验证。

候选新卡用实测单卡速度比 `S` 与跨卡效率 `η` 换算：`所需卡数 ≥ ceil(269.30 / (目标小时 × S × η))`，同时满足上述关键路径。不能把标称 FLOPS 或 HBM 带宽直接当成 `S`。[NVIDIA 官方 HGX 规格](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory/latest/components.html)给出的 H200/B200/B300 显存为 141/180/288 GB，但本任务在这些卡上的 Protenix 吞吐尚未测量。采购前应在候选机器上跑 100–500 条覆盖真实长度分布的单卡基准，再做八卡和跨节点短测，测出 `S`、`η`、正例冷读吞吐、GPU 峰值和网络传输。单台八卡 B300 的 2.3 TB HBM 也不足以容纳 5.35 TB 正例缓存；若坚持零特征读盘，需额外主机内存或重新计算正例。
